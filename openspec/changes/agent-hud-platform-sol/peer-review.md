# Peer review of the Astra platform proposal

Author note: Independent peer-review pass under the requested author profile `gpt-6.1-sol` with `max` reasoning.

Reviewed Astra's complete proposal, design, tasks, and all nine capability specs, then reread the complete Sol change against the expanded [FEATURES.md](../../../FEATURES.md) and the local OpenSpec artifact instructions. No web or external sources were used. This review changes only the Sol alternative; it does not select an implementation plan or establish provider compatibility.

## Concrete strengths

- **Trust and accounting are treated as contracts.** [State contract](../agent-hud-platform-astra/specs/hud-state-contract/spec.md), lines 29–63, requires coherent revisions, independent trust dimensions, dependency provenance, and explicit parent/child inclusion. [Design](../agent-hud-platform-astra/design.md), decisions 3–5, rejects recency-based binding and cross-source clock comparisons. These directly support the roadmap's identity, synchronization, and unknown-value requirements.
- **Privacy includes previously retained data.** Design decision 8 and [privacy spec](../agent-hud-platform-astra/specs/hud-configuration-privacy/spec.md), lines 35–58, cover frozen views, HUD-owned logs, private resources, separate display/retention consent, and the limits of recalling exports. This is stronger than render-only redaction.
- **Delivery and verification are explicit.** Design decisions 11–12 and [tasks](../agent-hud-platform-astra/tasks.md), groups 9 and 15–16, distinguish the MVP milestone from full change completion, require real provider evidence, and measure aggregate process costs. Every capability has Purpose, ADDED requirements, normative language, and four-level WHEN/THEN scenarios; the capability names match its nine spec directories.

## Findings and better alternatives

1. **High — additive compatibility is underspecified.** State-contract lines 7–16 promise compatible additive minor versions, but design line 49 rejects unknown common keys. No negotiated minor-schema or safe skip rule reconciles those behaviors. Negotiate mandatory features and explicitly skip bounded unknown optional telemetry without retaining it; keep configuration typos, invalid known fields, and unknown operations as errors. Add an unknown-common-field scenario, not only a namespaced-extension example.

2. **High — reset and snapshot wording is weaker than the design.** State-contract line 55 begins an epoch for cumulative resets; design line 136 correctly requires proof of reset rather than merely a falling counter. The spec needs that negative scenario. Its line 19 also says snapshots replace an owned scope, while design line 61 replaces declared field groups within a scope. Specify authorized coverage and collection ownership so one source cannot clear another's fields. Retain Sol's existing atomic capability-withdrawal rule, which Astra does not state explicitly.

3. **High — reconnect needs an action-safety contract.** Astra separates control from rendering and leaves unknown approvals pending ([adapter spec](../agent-hud-platform-astra/specs/hud-adapter-integrations/spec.md), lines 28–44; design line 184). However, tasks 13.4–13.5 do not specify stale approval responses, reused request IDs, or an input whose delivery outcome is unknown after disconnect. Bind decisions to verified session/request identity and reject retired requests; never automatically replay input, cancellation, or approvals without proven idempotency and reconciliation. Adopt its minimal built-in control surface to remove Sol's dependency on an unspecified external compatible client.

4. **Medium — privacy reload can race with an output already prepared.** Privacy-spec lines 36–44 require purging before further output; design line 164 resets buffered exports. Neither defines what happens when an asynchronous writer holds an old permitted projection. Gate each sink write on the current privacy revision, cancel/rebuild pending exports, and purge rotated HUD logs. Document that already completed user exports cannot be recalled. Also stage identity-affecting configuration changes through a fresh binding generation.

5. **Medium — recovery and performance promises need a workload boundary.** Design lines 118 and 124 allow multi-slice replay, while line 224 promises recovery within two reconciliation periods regardless of baseline size. A large log or sustained producer can exceed that time even after source identity stabilizes. Bound total recovery work and replay staging, publish progress/uncertainty, and limit the convergence deadline to a documented baseline workload. Adopt the 100-events/s active workload and numeric idle-I/O/probe ceilings; retain Sol's existing CPU/RSS/latency targets until measurements justify an explicit revision.

6. **Medium — security details need acceptance scenarios.** Design line 192 specifies DNS address pinning, redirect isolation, and minimal command environments, but [activity/usage spec](../agent-hud-platform-astra/specs/hud-activity-usage/spec.md), lines 56–65, tests only a changed host and a timeout. Make DNS rebinding, dual-stack/private addresses, request-scoped credentials, and environment-only attempts to enable queries contract cases. Private endpoint nonces protect against accidental cross-session routing within the same user's trust domain; they are not a sandbox against that user's code.

7. **Scope and UX — preserve evidence before expanding claims.** Astra requires structured Codex/Claude smoke evidence before completion (design line 180), but adds macOS and a complete controlled client to a repository with no product code. Those are substantial delivery obligations. Keep Sol's Linux architecture scope, add explicit evidence gates for its required structured modes, and split the client work into reviewable tasks. Adopt keyed tool/subagent/quota upserts/removals (design line 61) and the no-tmux second-terminal attach instruction (line 148). Neither should weaken exact child-argv preservation, focused-input ownership, or the roadmap's deferral of a shared public bus.

## Sol reconciliation

The accompanying revision keeps Sol's nine capability names and separate `usage-limits` boundary. It adopts keyed collection patches, dependency-aware trust, controller-stamped ingress metadata, new generations on detach/rebind, bounded replay, a minimal controlled client, privacy/export barriers, destination pinning, stronger support evidence, and measurable source-I/O/load gates. Each adopted behavior is carried into the relevant specs, design, and unchecked implementation tasks. Strict OpenSpec validation is necessary for structural correctness; the behavioral findings above require the planned acceptance evidence as well.
